# Research: Recreate the Pi Web Agent

## Research Question

Research the implementation landscape implied by `docs/initial-prompt.md`, including the Pi extension backend, local HTTP bridge, streaming protocol, and React frontend boundaries.

## Summary

The repository does not yet contain a web agent implementation; `docs/initial-prompt.md` is the only feature artifact in-tree. The prompt already fixes the two implementation roots: `.pi/extensions/web-agent/index.ts` for the backend bridge and `web/pi-web-ui/` for the browser app (`docs/initial-prompt.md:16-17,19,39`).

The backend can be grounded on existing Pi SDK primitives: browser sessions should be isolated `AgentSession` instances created with `SessionManager.inMemory()` and `DefaultResourceLoader`, while the bridge owns the loopback HTTP server, auth gate, session map, NDJSON translation, and TTL cleanup (`docs/initial-prompt.md:21-25`; `examples/sdk/06-extensions.ts:26-43`; `examples/sdk/11-sessions.ts:9-13`).

The main architectural gap is protocol adaptation: Pi already emits native `AgentSessionEvent` streams and ships newline-delimited JSON framing helpers, but the prompt’s browser protocol uses different event names (`status`, `assistant_delta`, `tool_*`, `done`, `error`), so the bridge needs an explicit translation layer between runtime events and frontend state (`docs/initial-prompt.md:35-37,60-63`; `dist/modes/rpc/rpc-mode.js:261-263`; `dist/modes/rpc/jsonl.js:8-38`).

## Detailed Findings

### Backend bridge and extension boundary

- The prompt explicitly assigns Layer 2 ownership to `.pi/extensions/web-agent/index.ts` and gives it responsibility for server lifecycle, auth, asset serving, and browser session lookup/creation (`docs/initial-prompt.md:16,19-25`).
- Pi extension discovery supports that exact placement: project-local extensions can live at `.pi/extensions/*/index.ts` (`docs/extensions.md:105-112`).
- The documented multi-file extension pattern keeps helper modules adjacent to `index.ts`, which fits a web-agent split like `auth.ts`, `session-store.ts`, `meta.ts`, and `protocol.ts` under `.pi/extensions/web-agent/` (`docs/extensions.md:228-235`).
- Existing extension examples follow that colocated-helper pattern instead of introducing separate backend packages (`examples/extensions/plan-mode/index.ts:19`; `examples/extensions/doom-overlay/index.ts:13-15`).

### Browser-isolated session model

- The prompt requires an in-memory map of `WebSession` objects keyed by browser `sessionId`, isolated from terminal chat history (`docs/initial-prompt.md:21-25`).
- Pi SDK provides the necessary isolation primitive through `SessionManager.inMemory()` (`examples/sdk/11-sessions.ts:9-13`; `dist/core/session-manager.d.ts:311`).
- Pi SDK also exposes `createAgentSession()` with a `resourceLoader` and `sessionManager` override, which is the concrete constructor the bridge would use for browser sessions (`docs/sdk.md:54-59`; `dist/core/sdk.d.ts:44-49,106`).
- The prompt’s `DefaultResourceLoader` requirement is aligned with SDK behavior: it is the standard discovery mechanism for extensions, skills, prompts, themes, and context files (`docs/initial-prompt.md:23`; `dist/core/resource-loader.d.ts:56-72,109-150`).
- Because the SDK does not define a built-in `WebSession` type, that wrapper must be local to the extension and should at minimum carry the browser `sessionId`, the underlying `AgentSession`, and liveness fields such as `lastAccessAt` (`docs/initial-prompt.md:21-25`; `dist/index.d.ts:2,14-16`).

### Auth and server hardening

- The prompt defines token auth as the concrete default: protect all `/api/*` routes using `x-pi-web-token` with timing-safe comparison (`docs/initial-prompt.md:31`).
- It separately defines `/health` as a coarse operational endpoint returning values like `cwd` and `sessionCount`, which makes `/health` the natural unauthenticated route while `/api/session/meta` and `/api/chat/stream` stay behind the token gate (`docs/initial-prompt.md:33-37`).
- Startup config concerns are distinct from per-request auth: bind to `127.0.0.1` by default, allow env overrides, and generate a random token if none is provided (`docs/initial-prompt.md:53-54`).
- Response hardening is global, not route-local: restrictive CSP, `no-store`, and frame-deny headers must apply to API responses and any served frontend assets (`docs/initial-prompt.md:55`).
- Developer decision recorded during checkpoint: carry forward token auth first, but leave an explicit extension point for later OIDC support.

### Streaming protocol and NDJSON translation

- The prompt requires `POST /api/chat/stream` to use NDJSON and emit event types including `status`, `thinking`, `assistant_delta`, `tool_start`, `tool_update`, `tool_end`, `done`, and `error` (`docs/initial-prompt.md:35-37`).
- Pi SDK already exposes live event subscription through `AgentSession.subscribe(listener)` (`docs/sdk.md:84`; `dist/core/agent-session.d.ts:72-73`).
- Pi runtime already has JSONL/NDJSON framing helpers that serialize one JSON object per line and parse LF-delimited streams robustly (`dist/modes/rpc/jsonl.js:8-38`).
- Pi RPC mode is the closest producer precedent: it subscribes to a session and writes each event as a JSON line (`dist/modes/rpc/rpc-mode.js:261-263`).
- The key mismatch is vocabulary: native runtime events are things like `message_update`, `tool_execution_start`, `tool_execution_update`, `tool_execution_end`, and `agent_end`, while the prompt’s web protocol expects browser-friendly names (`@earendil-works/pi-agent-core/dist/types.d.ts:345-366`; `docs/initial-prompt.md:35-37`).
- Therefore the backend must normalize native session events into a dedicated web protocol instead of exposing raw `AgentSessionEvent` objects directly.

### Frontend shell and stream consumer

- The frontend implementation root is fixed by the prompt at `web/pi-web-ui/`, with a Vite/React/TypeScript/Tailwind/shadcn stack (`docs/initial-prompt.md:39-42`).
- The shell is already decomposed by the prompt into three zones: fixed header, scrollable message/current-run area, and fixed footer with prompt controls (`docs/initial-prompt.md:43-46`).
- The browser persistence boundary is explicit: auth token belongs in `sessionStorage`, while `sessionId` belongs in `localStorage` (`docs/initial-prompt.md:17`).
- The stream consumer must maintain both durable history and an in-progress `currentRun`, because the prompt distinguishes “message history” from “current run” and only finalizes on `done` (`docs/initial-prompt.md:45,62-63`).
- Existing Pi client precedent for incremental consumption exists in the RPC example, which parses line-delimited JSON and updates UI state as events arrive (`examples/rpc-extension-ui.ts:512-570`).
- No `web/pi-web-ui/` files exist yet, so frontend module names such as `chat-header.tsx`, `status-strip.tsx`, `chat-history.tsx`, `chat-input.tsx`, `use-chat-stream.ts`, and `title-heuristic.ts` remain inferred file boundaries rather than discovered code.

### Session metadata, title, and status-strip sources of truth

- `/api/session/meta` is intended to return session-scoped data such as usage, model info, active tools, and resource health (`docs/initial-prompt.md:34,44-48`).
- Pi SDK already provides a public session stats API that aggregates tokens, cost, and context-window usage: `AgentSession.getSessionStats()` (`dist/core/agent-session.d.ts:548-565`; `dist/core/agent-session.js:2336-2402`).
- Model and thinking state are directly available from `session.model` and `session.thinkingLevel` (`dist/core/agent-session.d.ts:255-259`).
- Active tool names and tool inventory can be read from `session.getActiveToolNames()` and `session.getAllTools()` (`dist/core/agent-session.d.ts:265-275`; `dist/core/agent-session.js:545-557`).
- Skill/prompt/theme counts and diagnostics come from the resource loader, while extension load failures are reported separately via `LoadExtensionsResult.errors`, so the bridge must normalize those into one resource-health payload (`dist/core/resource-loader.d.ts:20-42`; `dist/core/extensions/types.d.ts:1158-1165`; `dist/core/diagnostics.d.ts:1-10`).
- The prompt’s “editable conversation title” should be backend-canonical, not browser-only. Pi already persists titles via `session_info` entries and exposes them as `session.sessionName` plus `session.setSessionName()` (`docs/initial-prompt.md:44,48`; `dist/core/session-manager.d.ts:76-79,121-127,209-211`; `dist/core/session-manager.js:2402-2417`; `dist/core/agent-session.js:2129-2131`).
- The frontend title heuristic is therefore a fallback only: generate locally when backend title is absent, then sync back to backend persistence.

### Control semantics: Send, Stop, Reset

- Send is defined by the prompt’s data flow: POST prompt JSON to `/api/chat/stream`, update the UI incrementally from NDJSON, then refresh metadata on `done` (`docs/initial-prompt.md:59-64`).
- Stop has a concrete backend analogue in `AgentSession.abort()` (`dist/core/agent-session.d.ts:248`).
- Reset is the main unresolved product boundary. Pi has root-reset mechanics through `SessionManager.resetLeaf()` and root navigation logic (`dist/core/session-manager.d.ts:278`; `dist/core/agent-session.js:2270-2276`), but the prompt does not yet say whether Reset should clear the existing browser session or replace it with a fresh isolated `AgentSession`.

## Architecture Insights

- The cleanest boundary is a thin HTTP bridge over existing Pi runtime primitives rather than a custom agent stack.
- The browser bridge should own browser identity (`sessionId`) and liveness, while the underlying `AgentSession` remains the source of truth for history, model state, usage, tool state, and title.
- The prompt’s web protocol should be explicit and stable; exposing raw `AgentSessionEvent` objects would leak internal runtime semantics into the frontend and make UI state harder to normalize.
- Resource-health reporting is broader than extension load success. Skills, prompts, themes, and extensions each surface diagnostics differently, so the metadata route should normalize them before the UI consumes them.
- The backend title model is already solved by Pi session metadata; frontend heuristics should improve first-run UX, not redefine ownership.
- OIDC should be treated as a future-facing extension seam layered over the token-auth baseline, not as the initial core of the bridge.

### Composite Lessons

- Prefer the documented multi-file extension layout over inventing a separate backend package for the bridge (`docs/extensions.md:228-235`; `examples/extensions/plan-mode/index.ts:19`).
- Use `SessionManager.inMemory()` plus `DefaultResourceLoader` to create browser-isolated sessions that still see normal Pi resources (`examples/sdk/06-extensions.ts:26-43`; `examples/sdk/11-sessions.ts:9-13`).
- Keep the web transport protocol explicit and translated; Pi’s RPC/JSONL utilities are a precedent for framing, but not for exposing raw runtime discriminants directly to the browser (`dist/modes/rpc/rpc-mode.js:261-263`; `dist/modes/rpc/jsonl.js:8-38`; `docs/initial-prompt.md:35-37`).
- Treat backend title persistence as canonical and the frontend heuristic as a fallback-only UX enhancement (`docs/initial-prompt.md:48`; `dist/core/agent-session.js:2129-2131`; `dist/core/session-manager.js:2402-2417`).
